## 保留机制一：看当前分支，也看决定能到这里的分段

context.vim 的 owning source 很明确：普通行向上找严格更小的缩进；`should_extend` 成立时允许同一级。因此读 `else` 时能够把对应的前分段放回视野，而不是只显示函数名。它还按 `changedtick` 失效缓存，并按每层高度预算压缩。**这些是编辑器的源码上下文选择，不是证明条件已经发生。** 固定 C fixture 完整 10,898 bytes，SHA-256 `481ca91a2baff12b828c2f3c45c213102bbc520f1f310bb1ca80dbdb8c0fd405`；本轮未运行插件或该文件。

vim-matchup 的 open/mid/close 搜索补充了“当前分段、前后界标、完整外围结构”三种范围。能借的是阅读组织：在一份作者已核定的条件表旁放关联源码范围，并说明哪些分支未走才会到后继；不是从缩进自动推导动态路径，也不将光标所在位置当程序正在执行的位置。

曾考虑的具体问题是：“没有传 `--browser-check`，为什么 native finalize 仍检查浏览器？”3f95 的 [runFinalize L732–746](https://github.com/tt-a1i/archify/blob/3f95f0349c8276db71509ca239461b6fe9d00f9f/archify/bin/finalize.mjs#L732-L746)以 `type !== 'explainer' || browserCheck` 决定请求，与 quality 是否 standard 没有直接条件关系；[初始 receipt](https://github.com/tt-a1i/archify/blob/3f95f0349c8276db71509ca239461b6fe9d00f9f/archify/bin/finalize.mjs#L795-L796)的 requested/ran 分开；[L907](https://github.com/tt-a1i/archify/blob/3f95f0349c8276db71509ca239461b6fe9d00f9f/archify/bin/finalize.mjs#L907)又以 browser receipt 的 viewport 记录是否存在赋值 ran，不能把它泛称为“调用了子进程”；[失败处 break](https://github.com/tt-a1i/archify/blob/3f95f0349c8276db71509ca239461b6fe9d00f9f/archify/bin/finalize.mjs#L996-L1005)保留未到后续阶段的可能。相应 [test](https://github.com/tt-a1i/archify/blob/3f95f0349c8276db71509ca239461b6fe9d00f9f/test/finalize.test.mjs#L189-L224)使用注入 runner，不能当实际浏览器执行证据。

按协调者要求，另完整读了已发布 [delivery-witness README](https://github.com/tt-a1i/archify/blob/f2aa251e4e8f93cd6f409df0adaa1b11b368e2e1/experiments/delivery-witness/README.md)、[实际 Explainer document](https://github.com/tt-a1i/archify/blob/f2aa251e4e8f93cd6f409df0adaa1b11b368e2e1/experiments/delivery-witness/witness.explainer.json)及其产物绑定。它解释 Moirae 同刻 seq/dup/raw patch，不包含上述 finalize 条件导读；其机器 gate/截图/用户收益也已分开记账。主题没有直接重复，但再做一份条件流程页与已有 source-question-tour、repository-orientation 的方法成本相近，暂没有独立阅读收益证据，而且新 dev 已修改 finalize。因此**不实施新页面或通用 condition viewer**，只留下固定旧版本源码判断供文档准确性核查。

## 保留机制二：比较两个范围，不先假设它们是同一文件的前后版本

Linediff 的 [公开 spec](https://github.com/AndrewRadev/linediff.vim/blob/5ed585de3af720f86e895590ad30694145879e2b/spec/plugin/basic_spec.rb#L7-L34)先选择同文件两个三行块，再核对两个临时 buffer 的内容。这份完整 spec 为 1,055 bytes，SHA-256 `3b2f1a93f327ef95d2464b563c600d9c81bf9955cd85e109573b28cd50229339`。源码为每个范围保留原 buffer、from/to 与说明；其回写能力是真正的编辑器行为，Archify 不应一并带入。

对 Archify 最小可复用合同是两边分别明确 `revision + path + start/end + excerpt digest`，说明为什么作者认为值得比较；相同行号、相同函数名、相同文本都不证明同一语义身份。现有 Explainer 的 code/source/diff block 已能展示这样的 authored 对照，task-review-map 则限定真实 Git 两侧范围记账，二者不能混成同一种“验证”。

一个可用的阅读问题是 canonical SVG 规则与 preview CSS override 为什么得到不同颜色。但 preview-dashed-ink 已用同一完整官方输入、静态 SVG/child 一致和前后 computed color 证据解决该具体问题，另造一份比较页目前没有新增收益。保留这种选范围的方法；出现真正需要比较两段非对应代码的任务时再挑完整公开输入，不为它先写 parser、merge/editor 或跨项目 diff 服务。

gron 与 Comby 则是范围合同的旁证：gron 的两个固定配对文件分别为 205/267 bytes（SHA `ec715ce1782966811f1f931e9a0d8c792cc005d75280a47695557571b08728d3` / `917fdb2d7dd87299ebd6dd172408136609c9c83aab45ff499d450d5fae084e27`）；Comby 的 `test_match_offsets.ml` 为 3,669 bytes，SHA `1566082ca0f1d8d6ef1579ec1f0cc41c7692973e7a924349e6d5a833994e2ecd`。二者都让路径/区间可检查，但没有替读者证明领域语义。
